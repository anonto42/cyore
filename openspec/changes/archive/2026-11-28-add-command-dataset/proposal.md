# Proposal

## Why

Stage 1 is done (`xor`, `mnist`). Stage 2 of the learning plan (README.md) trains a model that maps plain-English requests to terminal commands, starting with an intent classifier and a slot model. Neither can be built without training data, and the plan calls for "50–100 commands, 20+ phrasings each, a few thousand examples, with variations generated by scripts". This change builds that dataset first, as its own milestone, so the model change that follows can focus purely on Burn and training.

## What Changes

- Add a workspace crate `dataset/` with a generator binary that writes a reproducible command dataset from a hand-written catalog.
- The catalog defines at least 50 command intents (plus an `unknown` intent for out-of-scope requests). Each intent has a command template with named slots (e.g. `ls -la {dir?}`) and a small phrasing grammar (`(show|list) [me] the files in {dir}`) that expands to 20+ distinct phrasings.
- Slot values (folders, file names, patterns, hosts, process and program names) come from fixed pools split into training-only and test-only values.
- Output, written to the git-ignored `data/commands/`:
  - `train.jsonl`: a few thousand generated examples (text, tokens, BIO slot tags, intent, slot values, filled-in command)
  - `test.jsonl`: hand-written, natural phrasings that never appear in training, using unseen slot values, to measure generalisation
  - `intents.json`: the label list (intent names, command templates, slot names)
- Built-in validation: the generator refuses to write a dataset that has inconsistent slots, too few phrasings, train/test overlap, or any command outside the allowlist or matching the safety blocklist.
- A `make commands-data` target, and updates to `AGENTS.md` and `.agents/shared/memory/project-status.md`.

### Non-goals

- No model, no Burn dependency, no training. The intent classifier and slot model are the next change.
- No destructive or state-changing commands beyond creating a directory or an empty file: no `rm`, `mv`, `cp`, `chmod`, `kill`, `sudo`, package managers, or shell pipelines. Leaving them out of the dataset means the model can never suggest them, a first safety layer ahead of the Stage 3 agent's own checks.
- No multi-word slot values, multi-step requests, or languages other than English.
- No seq2seq targets beyond the filled-in `command` string (kept so the later transformer can reuse the data).

### Invariants

- Learning-plan stage: Stage 2 (first change).
- `xor` and `mnist` and their specs are untouched.
- The same seed produces byte-identical output files.
- `make check` stays green without generated data (tests build small catalogs in memory and validate the real catalog without writing files).
- Every command in the dataset passes `.agents/shared/rules/safety.md`'s blocklist.

## Capabilities

### New Capabilities
- `command-dataset`: the catalog of intents, slots, and phrasings, and the generated, validated training and test files that the Stage 2 models consume.

### Modified Capabilities

None.

## Impact

- New: `dataset/` crate (workspace member), `data/commands/` (already git-ignored via `data/`).
- Changed: root `Cargo.toml` (members), `Cargo.lock`, `Makefile` (one target), `AGENTS.md`, `.agents/shared/memory/project-status.md`.
- New dependencies, only in the `dataset` generator, never in a shipped binary: `serde` and `serde_json` for writing and checking JSON (justified in design.md).
- No effect on the `xor` or `mnist` binaries or the Docker image.
